CASE STUDY · FRAMEWORK PORT · AI CLAIM VERIFICATION ON LANGGRAPH

Rebuilt on LangGraph, it scored the same, and its harness grew from 509 to 585 lines instead of shrinking.

parity run · 2026-07-20 · p3-official-2026-07-20 neutral-name re-run · 2026-10-13 · official-rerun-2026-10-13 repo verified @ f969a98 RESULT: GATE PASS ON BOTH RUNS · PRECISION 1.00 · RECALL 1.00

Rebuilt on the LangGraph framework, the agent that checks facts on product pages and reviews against their sources passed the original's fixed test on 12 synthetic cases, all 35 claims right, before and after verdict words were removed from eight test folder names.

The problem

Product pages, reviews and other content pages make factual claims that should match their sources but usually go unchecked, and an agent free to act near live content cannot be trusted to check them. The original answer was a bounded agent, hand-built on the Claude Agent SDK, with four read-only tools and nothing else. That system has its own case study.

This repository asks a narrower, second question: if the same bounded agent is rebuilt on a popular agent framework instead of by hand, do its safety limits survive the move, and does the framework help or get in the way?

What was built, and the test it was held to

The port keeps the same four read-only tools, the same three verdicts (SUPPORTED, CONTRADICTED, UNVERIFIABLE) and the same comparison policy, and is built with LangChain v1's create_agent. The original enforces five limits: a fixed list of allowed tools, a cap of 20 turns, a cost ceiling per run, a counter that stops a run after too many tool calls, and an audit row written before a tool result reaches the model. In the port, the tool list given to the framework is the allowed list, and a framework component stops a run after 20 model calls. The rest is hand-written middleware, code that runs around every model and tool call. It adds up the cost of each model call. It refuses further tool calls once that cost passes the ceiling, or after the 60th tool call. And it writes an audit row to a local SQLite log before and after every tool call, refused calls included.

The test was fixed before the port existed. The 12 synthetic cases, the answer key and the file holding the pass mark and the comparison policy are copied from the original: at the port's first code commit they are byte for byte the original's files. The original's runner cannot drive the framework, so the port has its own, which scores with the same matching rule and metric definitions. The pass mark, the gate, is the original's: precision at least 0.95 and recall at least 0.90, with CONTRADICTED as the positive class, over 8 truly contradicted claims among 35. Three cases are traps: a near-match number, a price spelled out in words, and a forum post repeating a figure against the manufacturer's spec sheet.

The first decision record was committed on 2026-07-18 (f25a66d), and the first agent code on 2026-07-20 (4550db7). That record fixed the rules: the existing scorer and thresholds decide PASS or FAIL, the result is published either way, and any move from fail to pass must be the port improving, never the ruler moving. It also registered a prediction: the tool list and turn cap could live in the framework, while the cost ceiling, the call counter and the audit would have to be hand-built, "because the framework offers no primitive for them."

The run

The official parity run, p3-official-2026-07-20, ran on 2026-07-20 with Claude Sonnet 4.6, the model of the original's gate run, one fresh agent invocation per case, with LangSmith tracing on. All 35 verdicts matched the answer key. No case hit the turn cap or the cost ceiling. Each case used 4 or 5 of its 20 model calls, and the run cost $0.6332 in total, $0.0442 to $0.0609 per case, against a ceiling of $1.50 per case.

The cost is the port's own accounting. The port calls the model through an API key billed per token, and the middleware multiplies each call's input and output tokens by the list prices in its configuration. It is not an invoice, and it is not measured the way the original's cost is.

What the record shows was wrong

The prediction placed two of the five limits wrongly, and the record publishes both. Of the three limits it said would need hand-building, only the cost ceiling did: the framework has no limit in money. It does have a tool-call limit (ToolCallLimitMiddleware) and a hook around every tool call (wrap_tool_call). The audit moved onto that hook. The hand-built call counter was kept anyway, as registered, and the second decision record states that the framework offers one.

The written plan also had a fact wrong about the original. It called audit rows written inside the tools the original's proven pattern. Checked against the original on 2026-07-20, the original's tools contain no audit code; its audit rows come from SDK hooks around the tools. The second decision record carries this as a dated correction and leaves the plan's text as committed.

The port also inherited the original's test folder names. Until 2026-10-13, 8 of the 12 case folder names contained a verdict word (supported, contradicted or unverifiable). The folder name reached the model in the user prompt, and the fetch_page tool description carried one old name, case_01_supported_wireless_earbuds, as its example path. On 2026-10-13 the folders were renamed case_01 to case_12 (0014334), the answer key changed by name substitution only, and the test suite gained a check that fails if any dataset name contains a verdict word. Then the frozen eval was run again: same dataset content, scorer, thresholds, model, ceiling and caps, one fresh invocation per case, no case re-run. Between the two runs the agent code changed only in that example path and in a 2026-07-24 fix that rejects backslash paths.

What this proves, and what it does not

It proves that on 12 hand-written cases the port passes the same frozen gate as the original, with every verdict correct, and still does when the folder names no longer carry verdict words. And it counted the code: the agent files hold 509 lines in the original and 585 in the port, counted as plain file lines with comments and blank lines included. The tools and audit files shrank by 69 lines together; the new middleware file adds 129.

Three of the five limits are tested in CI. A 22-test suite, which CI runs on Ubuntu, macOS and Windows with Python 3.12 and 3.14 on every push and pull request to main, calls the tools through the real middleware. It checks that the call counter trips after 60 calls, that tool calls are refused once the tracked cost passes the ceiling (the test sets that cost by hand; the cost adding-up itself is not tested), and that the audit row comes before the result row, on one normal and one refused call. It also checks that paths outside the dataset folder are rejected and that no dataset name carries a verdict word. A check that the answer key's claim IDs never appear in the audit log runs too, but in CI the log holds only the suite's own test calls. One test, which needs the audit log of a real run, is skipped in CI because no such log is committed (run at f969a98: 21 passed, 1 skipped on all six jobs). The turn cap and the tool list are set in code and not tested.

It does not prove the agent works on real web pages, and it is not a tight estimate: both runs caught all 8 contradicted claims, but with only 8, one miss would have meant 7 of 8 (0.875), below the 0.90 gate.

KNOWN LIMITATIONS, SELF-DECLARED

  • The eval runs on labeled synthetic pages by design; the system has not been deployed and carries no production or availability claim.
  • Parity was measured on one task family, one dataset and one model pair: evidence that the port kept the system's behaviour under its gate, not a general claim about either framework.
  • The trace archive of the July run is a record exported and committed by the repository author, not independently hosted evidence; the hosted LangSmith traces were due to expire about 14 days after the run.
  • Tracing was off for the October re-run, so it has no trace archive; its evidence is the committed runner output.
  • A development sweep on Claude Haiku 4.5 got all 12 cases right; its record calls that weak evidence for the official run.

The decision on record

DECISION 0001: PORT TARGET, CAGE TRANSLATION STRATEGY, EVAL-PARITY CONTRACT · DATED 2026-07-18 · ACCEPTED

The claim-verification agent was chosen as the port target over the compliance orchestrator for three reasons: it is a single agent, which fits a two-week part-time box; its frozen eval was already green, so parity asks a question that can fail; and its bounds suite is a ready-made checklist for translating the limits. It pre-registers the predictions "so the writeup's conclusions cannot be retro-fitted to whatever the port happened to do." The second decision record, dated 2026-07-20, scores them against the framework's live documentation: of the three limits said to have no framework tool, one held and two were wrong, all published, because "the writeup's evidence base is the tested record, not the prediction."

The comparison writeup is the deliverable of this port: what the framework gives, what it hides, and what it cannot enforce, limit by limit. Its conclusion is that the framework moved enforcement into an explicit middleware layer and did not remove the need to prove it, and that the test suite, not the framework, is what makes the limits trustworthy; in this port that suite covers three of the five.
