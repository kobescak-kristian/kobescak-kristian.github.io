Three jurisdictions, bounded agents, and a gate passed on 29 of 30 scenarios.

latest official series · 2026-11-05 · H2-2026-11-05-a7871a RESULT: PASS, 29 OF 30 first official run · 2026-07-09 · gate-9328e564 · gate v1.0 FAIL repo verified @ ef46410

Bounded AI agents check iGaming operator and affiliate pages against three synthetic rule sets, under deterministic control and human approval, and the system passed its latest official evaluation, gate v2.1: 29 of 30 synthetic compliance scenarios in all 3 runs, 52 of 52 deterministic checks, and 0 of 30 pages with a repeated material error.

The first official run, in July, failed its gate on precision. This page covers what that failure showed and what was repaired.

The problem

iGaming content, on operator and affiliate sites alike, can fall under several regulatory regimes at once (MGA, UKGC and German GlüStV-style themes). Content that is compliant in one jurisdiction can break the rules of another, rules change, and manual review is hard to scale. A single unbounded agent "checking compliance" is hard to trust or audit. A finding is only useful if it traces to a specific rule and a specific piece of evidence.

The rule sets here are synthetic: modelled on publicly known regulatory themes, not copied from real regulatory text, and not reviewed by counsel. The system demonstrates the orchestration pattern. It makes no claim of legal accuracy.

What was built

One checker agent per jurisdiction reads a page against its own rule set only. A second agent, the already published ai-claim-verification-agent, reused unmodified and pinned to one commit, re-checks each violation a checker reports and returns CONFIRMED, REJECTED or DISPUTED. A planner agent drafts a fix for confirmed violations only, and a human approves or rejects each fix in a command-line tool. Everything between the agents (task state, severity ranking, schema checks, dead-letter routing) is deterministic Python. No model decides what runs next.

Task states and agent tool calls are recorded in audit logs, and findings reference the applicable rule and supporting evidence.

SCOPE OF THIS RESULT

  • Pages and rule sets are synthetic, and no legal accuracy is claimed. This is one series on one purpose-written test set.
  • The new gate was written with knowledge of the July failure, and the test set, rule text and model also changed. The PASS shows success against that gate. It does not show that the system would meet July's precision and recall thresholds, and it is not a controlled before-and-after comparison.

What the first run found

All 8 misses (5 false positives, 3 false negatives) were in GBR and MLT; DEU scored clean. The July record read them as checker errors. A review on 2026-11-02 attributed 6 of the 8 to the page reader, which dropped every heading and list item, so the checker and the adjudicator never saw that text. That attribution comes from checking what the reader returned on the frozen pages, not from a model re-run. The record reads the other 2 misses as rule-interpretation errors: "risk-free" wording treated as a free-item claim, and a soft expiry reminder flagged as urgency pressure.

The adjudicator confirmed all 32 violation findings it was given, so it added no precision protection in that run, and it was reading the same truncated pages. Scores, thresholds and the FAIL stand as recorded. The run record analyses each miss.

What the repair changed

After the 2026-11-02 review, a repair program covered ten defects. The fixes that mattered most: the page reader now returns every text block; violation and compliance excerpts must appear on the page; a task that does not cover every rule is rejected; failed or missing results count as misses instead of going unscored; the verifier must run at its pinned version; agent calls have time limits; and page content is marked as data, not instructions.

Those fixes are shown by code and by regression tests (test_p2_repairs.py, test_run_eval.py; defect list in STATE.md), and that test suite was one of the 52 November checks. The November scores are a separate outcome, measured against the new gate. No measurement isolates what each fix contributed, because other things changed too (see the scope notes above).

What the evidence proves, and what it does not

The November series shows the complete system meeting a gate set before the run. It does not show 30 of 30, perfect accuracy, production readiness or legal compliance, and each scenario was scored on a decision chosen in advance, which does not show the system can screen a whole page. The adjudicator's value also remains unproven: it rejected no finding in either official run.

The July run proves the control plane held under one full official run on the synthetic eval set: 23 of 23 check tasks, 17 of 17 verify tasks and 32 of 32 plan tasks reached a terminal state, with zero lost and zero dead-lettered, and failure-injection tests FI-1 to FI-7 were green. A bounds check of the audit log found no reference to the answer-key file in any agent tool payload for the run.

It did not prove the detector accurate enough: it failed its precision gate. The idempotent re-run is shown by a unit test, not by repeating the run.

KNOWN LIMITATIONS, SELF-DECLARED

  • Rules are synthetic, modelled on public regulatory themes. The system demonstrates the governance pattern.
  • The July answer key was split across actors (spec and key: Claude; pages: Claude Code; blind labels: ChatGPT; adjudication: Kristian), which removes key-authorship leakage. The page author still knows what it planted, and pages, key and checkers share a model family.
  • Checker and verifier share a model. Adjudication guards against per-finding error, not model-family blind spots.
  • July counts per jurisdiction are small (MLT 7, GBR 13, DEU 10 violations). At recall ≥ 0.90, MLT tolerates zero misses before failing; GBR and DEU tolerate one each.
  • November pages and the draft key were written by fresh Claude contexts, the same model family as the checker, isolated by instruction. Blind labels came from a different model family.

The decision on record

ADR 0001: DETERMINISTIC CONTROL PLANE · ACCEPTED 2026-07-07

The orchestrator (task ledger, state machine, schema checks, dead-letter routing, resume from the ledger, severity ranking) is deterministic Python, and no model call starts in the control plane. Agents analyse and recommend; they never decide what runs next, a payload's severity, or whether a task is done. The trade-off is recorded: the system cannot adapt its routing to what an agent says. The build proves orchestration discipline, not routing intelligence.

On 2026-07-09 Kristian decided to publish the FAIL as the final v1.0 result, with no re-run in that cycle. The optional remediation pass left open that day has since run. Its cap of one re-gate was withdrawn on 2026-11-02, and its one official series under the new gate is the November result above (STATE.md at 91105ca).

Built with Claude coding agents, which are named as co-authors in the commit history. Decisions were Kristian's: opening the repair program, raising the evaluation level from the proposed Light to Standard, approving gate v2 and the revised rule text, and authorizing each phase and the one official series. Verification came from the committed gate and test suite, and from Kristian's adjudication of the July answer key and the answers where an independent model's labels disagreed with the draft key.

Across both evaluations the work follows one pattern: bound the agents, set the test before seeing the result, publish what happens, and repair from the evidence.
