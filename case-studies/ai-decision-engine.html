CASE STUDY · AUDIT REMEDIATION · AI DECISION ENGINE

Built to judge whether its decisions were right, it could quietly overwrite them.

remediation · 2026-07-05 to 2026-07-06 CI run 37558629364 · 2026-10-07 repo verified @ 70b09bf RESULT: 6 OF 6 CI JOBS GREEN · NO EVAL GATE

A lead-routing pipeline for sales teams that records each AI-assisted routing decision and later scores it against the recorded outcome; its fix commits record that a stored decision could be overwritten, one lead's outcome could be counted twice and a failed validation was discarded before it was stored, and after the fixes the demo passes a CI check on six configurations, on synthetic data.

The problem

The README starts from the premise that many AI lead-routing systems stop at classification. They decide where a lead should go, but they do not measure whether that decision was right. The failure is silent: sales teams receive unqualified leads, real buyers are missed, and nothing exists to detect or correct it.

This system records the original decision, accepts the real-world outcome later, and evaluates decision quality over time.

What was built, and the test it is held to

A lead goes through a model classification (OpenAI gpt-4o-mini), a validation step, a fallback to a safe default when the output fails validation, and routing to one of three decisions: send to sales, archive, or manual review. Each decision is stored in SQLite. The outcome is recorded later, through its own API endpoint, in a separate table. An evaluator joins the two and computes the conversion rate of leads sent to sales, the false-positive rate (leads sent to sales that did not convert), and missed opportunities (archived or manual-review leads that converted). Below 30% outcome coverage it reports "insufficient data" instead of a verdict. The thresholds it checks against are static settings, with defaults of at least 40% conversion, at most 30% false positives and at most 25% manual review.

This repository has no eval gate committed before a run. The check it is held to is a regression test, added on 2026-07-27 after the fixes described below. It runs the pipeline and the outcome-seeding script with an empty API key and asserts seven output lines and both exit codes. It runs on Ubuntu, macOS and Windows with Python 3.12 and 3.14, on every push and pull request to main. The expected lines were frozen from fresh-clone runs: two identical runs and one with a varied hash seed, per Python version.

What the record said, and what the code did

The README's own figures were corrected first. On 2026-06-20 the manual-review count went from 12 to 11, and the conversion rate from 72% to 68%. The commit that changed the conversion rate records that 72% and 32% together are impossible with 25 leads sent to sales; the commit that changed the count gives no reason. Both figures had been in the README since the first commit, on 2026-04-23.

An audit followed. Its report is not in the repository, and the repository does not say who ran it; its findings are known from the fix commits of 2026-07-05 and 2026-07-06, recorded in the README's version log as versions 1.1 to 1.4. Each row below sets a defect beside the README or decision-record line nearest to it.

Setup: copy the example settings file; the system "runs in simulation mode without an OPENAI_API_KEY". The example file held a placeholder key, which counted as set, so simulation mode was off. The documented quickstart sent all 50 demo leads to manual review and still exited with success. The example key is empty, a placeholder counts as no key, and the run prints its mode and the reason. f9d3230
The README described the fallback as handling malformed AI responses ("prevents system failure"); nothing covered a rejected key or an unreachable API. A rejected API key silently turned every lead into a manual-review fallback while the run reported success. After that fix, a re-verification found that an unreachable API did the same, with the real error replaced by a generic message. An invalid key, an unreachable API, or three consecutive identical AI-layer failures now stop the run with a non-zero exit and the named cause; the real error is stored as the fallback reason. f9d3230 1449b44
The decision record: each decision is "one row per lead, written once". When a lead was processed again, saving its decision replaced the earlier row. The audit showed that tuning the threshold and re-qualifying one lead rewrote the history and cleared an active false-positive warning with no new outcome data. Decisions are append-only, one version per re-qualification, and the full history of a lead is readable through the API. b445c94
The outcome endpoint records "the real-world outcome for a decision". Nothing stopped a second outcome for the same lead. The audit showed one lead counted as both a conversion and a false positive, with the two rates summing to 104%. One outcome per lead; a second one is rejected with a 409 that names the existing outcome. The seeding script skips recorded leads instead of deleting and re-inserting them. 780cdf9
Persistence "creates an audit trail for every decision". An output that failed validation was still kept out of routing, but the code then re-validated the safe default, which always passes, and kept that result. The original failure was discarded before anything was stored; the decisions table had no validation column. Each stored decision keeps its original validation result and error, written once and shown in the audit endpoints. f1546c2

What this proves, and what it does not

It proves that, on synthetic data, the keyless pipeline produces the same routing split, zero fallbacks and the same seeded outcome coverage on six combinations of operating system and Python version, re-checked on every push and pull request.

It does not prove the quality of any model's decisions: the CI run never calls the model, the classifications come from a built-in table, and the outcomes are a fixed list written to include wrong decisions. The 68% and 32% describe the evaluator's arithmetic on designed data, not performance on real leads. The fixes themselves (append-only decisions, the 409 on a second outcome, the stored validation state, the abort paths) were verified by live runs: the commit messages state this and summarise the results, and the full output is not in the repository. Of the fixes, the CI check asserts only the two run-summary lines the first fix added: the simulation-mode banner and the fallback count.

KNOWN LIMITATIONS, SELF-DECLARED

  • Outcome correction is not supported in this version: an outcome, once recorded, cannot be changed through the API, and a second one is rejected.
  • Below 30% outcome coverage the system reports "insufficient data" instead of a number, so early in a rollout it cannot yet say whether it is working.
  • The coverage gate and the three evaluation thresholds are static settings, not learned; tuning them is a manual step.

The decision on record

ADR 0001: DECOUPLE DECISIONS AND OUTCOMES, JOIN ASYNC FOR EVALUATION · ACCEPTED · DATED 2026-07-04 · CLARIFIED 2026-07-06

Decisions and outcomes are stored in two separate tables, linked only by the lead ID. The decision is made at processing time with the information available then; the outcome arrives later, from a different source. The evaluator computes conversion, false positives and missed opportunities from the joined tables, never from the decision record alone. An outcome for an unknown lead fails loudly instead of creating an orphan record. It was chosen over writing the outcome onto the decision record, which would mix the quality of the decision with the later result and could not show "outcome not known yet". The trade-off is recorded: below 30% coverage there is no quality number, and the thresholds are tuned by hand.

The record's status reads "Accepted (implemented)". Its "written once" line did not hold in the code until the 2026-07-06 fix, and the clarification of that date says so and names the versioned append as the mechanism that makes it true. A next step the README points to is outcome correction, which it lists as a known limitation of this version: a recorded outcome cannot be changed through the API.
