A lead-routing workflow for operations and sales teams, with an AI agent that may only recommend: its fix commits record that the README described automated checks the demo could not fire and a duplicate flag the code did not store, and after the fixes the demo, on synthetic data, passes a CI check on six configurations.

The problem

Lead workflows are easy to start and hard to keep honest. Leads arrive from different channels in different shapes, get scored and routed, and move through stages. Many automations handle intake inconsistently, route on logic that cannot be audited, and cannot show where leads stall or why. When an AI is added, it often acts on the workflow directly, so a bad suggestion becomes a bad state change with no way back.

The system is for operations and sales teams that need lead handling to be deterministic and auditable, with AI used for insight rather than uncontrolled action.

What was built, and the test it is held to

Leads arrive from three source types (web form, email, ad platform). Each is normalised into one validated schema, scored, and routed by fixed rules to one of five named queues and a stage in a fixed lifecycle: new, qualified, assigned, contacted, proposal, then won or lost. Every stage change is stored in SQLite with its trigger and time, so the path of any lead can be rebuilt. A metrics step computes stage counts, stuck and aging leads, and queue workload. Nine API endpoints expose the state.

The AI part is one agent (OpenAI gpt-4o-mini) that reads the computed metrics and returns structured recommendations, each with an expected effect and a trade-off. It changes no lead, stage or queue. With no API key, or when the call fails, a deterministic function over the same metrics answers instead.

This repository has no eval gate committed before a run. The check it is held to is a regression test, added on 2026-07-27 after the fixes described below. It runs the demo with an empty API key and asserts six output lines that do not depend on the date. It runs on Ubuntu, macOS and Windows with Python 3.12 and 3.14, on every push and pull request to main. The expected lines were frozen from fresh-clone runs: two identical runs and one with a varied hash seed, per Python version.

What the README said, and what the code did

The README carried the first three claims below from its case-study version of 2026-06-17. The copy step in the fourth row was there from the first README, and its wording about the optional key dates from 2026-06-20, from a first round of audit fixes that did not fix any of the four. The fix commits of 2026-07-06 and 2026-07-07, released as the 2026-07-07 remediation release, record what the code actually did. The audit report itself is not in the repository; its findings are known from these commits.

What the README saidWhat the code didThe fix
Automated checks surface overdue, stuck and stale leads, "without manual triggering". In the demo run, all three checks could never fire. Ingest stamped every lead as updated "now", so none could look stale, and no seeded lead could reach the assigned or contacted stage before the checks ran. Ingest keeps each lead's own arrival time, and the demo ages two leads by fixed day offsets. "Without manual triggering" became "on demand". 0a12a5f
Duplicates are "flagged, not dropped". A repeated lead was skipped with a log line. No flag was stored, and a repeat with different data was skipped the same way. Same data returns 200 and increments a stored duplicate count; different data returns 409 and leaves the stored lead untouched. d592705
Leads are routed to named queues, including a manual review queue. No lead could score low enough to reach manual review, and a lead moved there by a stage change kept its old queue. A missing company signal now lowers the score, and a move to manual review sets that queue. 5e72d58
Setup: copy the example settings file; the API key is optional, and the agent falls back if it is unset. The example file held a placeholder API key, which counted as set, so the demo fired a live API call with it before falling back. The example key is empty, and a placeholder key counts as no key, with no network call. a5a9725

What this proves, and what it does not

It proves that, on synthetic data, the keyless demo produces the same counts on six combinations of operating system and Python version, re-checked on every push and pull request: leads ingested and failed, repeats flagged and rejected, the two backdated checks, and the deterministic source of the agent's answer.

It does not prove the quality of the agent's recommendations: the repository holds no evaluation of them, and the CI run never calls the model. It does not test the agent's boundary: that the agent changes no state is a design decision in the code and its decision record, and no test asserts it. The CI check does not assert manual-review routing or the placeholder-key path, and it does not cover the stuck-lead count, real CRM data, concurrent load or access control.

KNOWN LIMITATIONS, SELF-DECLARED

  • Synthetic data: the 74 leads and the 2 repeat fixtures are generated, not real CRM data.
  • No API authentication: the endpoints are open, and production would need authentication middleware.
  • SQLite does not support concurrent writes at high throughput; the named production upgrade is PostgreSQL.
  • The agent is stateless: it has no memory of earlier recommendations and no trend tracking across runs, and a person has to implement each recommendation.

The decision on record

ADR 0001: BOUNDED AGENT, RECOMMENDATION ONLY · ACCEPTED 2026-07-04 · REVISED 2026-07-07

The agent reads only computed metrics and returns structured recommendations (issue, recommendation, expected effect, trade-off, priority). It calls no function that changes lead state. If the API key is unset, empty or the known placeholder, or if the call fails for any reason, the code falls back to a pure function over the metrics with no external call. Scoring and routing run independently of the agent. The trade-off is recorded: recommendations are not applied automatically, so their value depends on a person acting on them, accepted as the cost of auditability.

The record's status reads "Accepted (implemented)", and the case-study README of 2026-06-17 already described an agent that recommends without changing state. The documentation pass of 2026-07-07 revised the record to add the placeholder-key fallback. One step the repository records as open is API authentication: the endpoints are open, and the README says production requires authentication middleware.
